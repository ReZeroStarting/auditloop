# auditloop 设计文档

> 版本 0.1.0 · 2026-10
> 这份文档的目标不是「介绍功能」，而是**把每个决定的理由和代价写清楚**。
> 面试时被追问「为什么不用 X」，答案应该能在这里找到一行。

---

## 0. 一句话定位

auditloop 是一个 **agent 运行时（harness）**：它不生产智能，它负责让模型的行为变成
**可拦截、可追溯、可验证**的事实。

模型是发动机，agent 是「怎么开」，harness 是底盘 + 线束 + 仪表盘 + 刹车。
这个项目做的是最后那个东西。

---

## 1. 问题定义

让模型去改真实仓库，失败几乎从来不是「写不出代码」，而是三类**静默失效**：

| 失效 | 现象 | 代价 |
|---|---|---|
| 乱来 | 删文件、越界改目录、跑危险命令 | 不可逆的数据损失 |
| 假完成 | 自称「改好了、测过了」，实际没跑或没通过 | 交付了坏东西，且没人知道 |
| 不可查 | 跑了 20 分钟后结果不对，现场已经没了 | 无法复盘，只能重跑，而重跑不一定复现 |

共同点：**它们都不报错。** 报错不可怕，「什么都没发生」才可怕。

所以设计目标不是「让它更聪明」，而是：

> 让每一次运行都留下一份能被别人复查的账本；让「完成」这件事有证据，而不是有说法。

---

## 2. 非目标

明确不做，才能在面试里答得干脆：

- **不做模型**：不训练、不微调、不做推理优化。
- **不做通用 agent 框架**：不提供「图编排」这种抽象。一个循环就是全部控制流；
  需要复杂编排时，用循环 + 子 agent，而不是引入 DAG 引擎。
- **不做沙箱**：策略层是**应用层约束**，不是内核层隔离。它防的是「模型无意越界」，
  不防「模型恶意逃逸」——真要跑不可信代码，必须上容器。
- **不做多租户服务**：当前形态是本地 CLI。要上线是一层 HTTP 的事，但不是 v0.1 的目标。

## 3. 一次 run 的时序

```
1. CLI 解析参数 → Config（环境变量 > toml > 默认；没 key 就退化成 MockLLM）
2. 建 TraceWriter → <state>/runs/<run_id>.jsonl，追加写 + 每条 flush
3. messages = [system, user(task)]
4. 循环（最多 max_steps 次）：
   a. 预算检查       —— token / 金额到顶 → budget_exceeded，优雅收尾
   b. 上下文闸门     —— 截断长工具输出；超水位压缩；记 context.compacted
   c. 记 model.request
   d. 调上游         —— 失败重试 → 降级 → 仍失败则 model_error
   e. 记 model.response（含 message、usage、延迟）
   f. 无 tool_calls → 收尾
   g. 逐个工具调用：
        - 解析参数（失败 → 回填 ERROR，属于模型的错）
        - 策略判定（硬拒绝 / 只读 / 需审批）
        - 记 policy.decision（批准或拒绝都记）
        - 被拒 → 回填 DENIED，让模型换路；连续 3 次 → policy_blocked
        - 执行 → 记 tool.call / tool.result（含真实耗时与字节数）
        - 结果回填，进入下一轮
5. 验证门禁（如果有 --verify）：跑命令，记 verification
   rc != 0 → status = unverified（即使模型说完成）
6. 记 run.finished（状态、步数、token、成本、拒绝次数）
```

三种闸门（预算 / 策略 / 验证）与五种退出，是 entire 设计的骨架。

## 4. 数据契约

### 4.1 事件（账本的一行）

```json
{"seq": 4, "ts": "2026-10-31T14:03:21.512+00:00", "run_id": "20261031-220321-a1b2c3",
 "type": "tool.result", "span": "m2.t1", "parent": "m2",
 "payload": {"name": "fs_edit", "ok": true, "bytes": 29, "duration_ms": 1}}
```

| 字段 | 含义 | 为什么这么设计 |
|---|---|---|
| `seq` | 单调递增 | 并发写也不乱序；`seq` 断号 = 有事件丢了 |
| `span` / `parent` | 归属的调用树 | 一次模型调用下的多个工具调用要能分清 |
| `payload` | 自由字典 | 加字段不用迁移历史账本 |

**为什么是扁平 payload 而不是一堆强类型子类**：账本要同时给人看和给机器算。
十个类会让「加一个字段」变成一次 schema 迁移，而历史账本不能改。

### 4.2 评测任务

```json
{"id": "t04-deny-destructive", "prompt": "...", "files": {"app.py": "..."},
 "script": [{"tool": "shell", "args": {"command": "rm -rf ."}}],
 "checks": [{"type": "event_seen", "event": "policy.decision", "where": {"denied": true}}],
 "verify": "python -m pytest -q", "max_steps": 8, "tags": ["policy"]}
```

检查项是**声明式字典**，不是 Python 断言。因为任务集要给人补，
写一行 JSON 的门槛远低于写一段代码。

## 5. 逐层设计

### 5.1 模型层（`llm/`）

接口只有一个：`chat(messages, tools) -> LLMResponse`。

- `OpenAICompatLLM`：只用 `urllib`；429/5xx 才重试（重试一个「参数错了」只是烧钱）；
  统一两家的缓存命名字段（`prompt_cache_hit_tokens` / `prompt_tokens_details.cached_tokens`）。
- `ScriptedLLM`：按脚本吐工具调用，用于**确定性演示与评测**。
- `HeuristicMockLLM`：没配 key 时的兜底，让新人 clone 下来第一条命令就能跑。
- `ReplayLLM`：把账本里的响应当上游，用来做事后复盘。
- `FallbackLLM`：降级链。一次 429 不该等于一次任务失败。

**失败模式**：没有流式。一次性返回意味着长输出时用户干等——这是 P2 的活。

### 5.2 工具层（`tools/`）

一个工具 = 名字 + 说明 + JSON Schema + 实现 + `mutating` 标记。

**三层校验，缺一不可**，因为三类错误的上游处理方式完全不同：

| 层 | 错误归属 | 正确反应 |
|---|---|---|
| Schema（形状） | 模型 | 回填 `ERROR`，让它自己改参数 |
| 策略（允不允许） | 用户的选择 | 回填 `DENIED`，让它换路，且不要重试 |
| 执行（文件在不在） | 环境 | 如实上报，重试通常无用 |

把这三类混成一句 "error"，agent 就永远学不会纠错。

默认工具集刻意窄：读、写、改、列、找、搜、跑命令、待办、子 agent。
网络、数据库、浏览器都要显式打开——**每加一个工具，就多一条搞坏东西的路**。

### 5.3 策略层（`policy/`）

三档模式：`ask`（改状态要问）、`never`（只读）、`auto`（全自动）。

判定顺序不能反：

1. **硬拒绝**：命中破坏性命令清单（`rm -rf` / `del /f` / `format` / `curl|sh` …）→ 谁批都不行；
2. **只读放行**：`ls`、`cat`、`git status` 这类不改状态的，任何模式都放；
3. **需要审批**：其余交给模式决定。

**为什么硬拒绝和审批要分开**：审批是人的判断，会疲劳。`rm -rf` 这种东西不该进审批队列——
它根本不该被问。把「不该问的」和「该问的」混在一起，是审批失效的开始。

**默认没有审批者时一律拒绝**。「问不到人就默认同意」是绝大多数 agent 事故的起点。

**能力边界（必须主动承认）**：这是应用层约束。`shell` 工具本身能跑任意命令，
所以一个有恶意的模型理论上可以绕开路径监狱（比如 `python -c "open('/etc/passwd')"`）。
策略防的是**无意越界**，不是恶意逃逸。要防后者必须上容器。

### 5.4 上下文层（`context/`）

三件事：估算、截断、压缩。

- **估算**：中日韩字符按 1 token/字，ASCII 按 3.2 字符/token。偏保守。
  为什么不用真 tokenizer：少一个依赖，且偏差控制在 10% 内就够用了——预算本来就留了余量。
- **截断**：单条工具输出超限时保留头 70% + 尾 30%。
  开头有「发生了什么」，结尾有「最后的结果」，中间过程最不值钱。
- **压缩**：超水位时把旧消息压成一段**确定性摘要**，并明确标注它不是用户输入。

**为什么压缩不调模型**：调模型意味着压缩本身会漂移、会烧钱、会让回放不可复现。
代价是摘要信息量低（它是规则生成的），长任务会丢细节——这是明知的取舍。

**为什么摘要要标注「不是用户输入」**：不标注，模型会把摘要当成新指令，行为立刻跑偏。

**为什么必须对齐到 assistant 边界**：从中间硬切会让 `tool` 消息失去对应的 `tool_call`，
上游直接 400。这是真实踩过的坑，测试里有一条专门守它。

### 5.5 循环（`core/loop.py`）

约 250 行，是整个项目的重心。四种退出、三道闸门都在这里。

值得单独说的是**被拒之后的处理**：不是终止，而是把 `DENIED` 回填给模型并让它换路；
连续 3 次才停手。理由：模型第一次撞墙很可能是不知道边界，第二次才是真的固执。
但必须有个上限，否则它会用同一种方式烧完你的预算。

### 5.6 账本（`trace/`）

- 写：追加 + 每条 flush。崩了也要留下「崩之前做了什么」。
- 读：**坏行直接跳过**。进程被 kill 时最后一行常是半截 JSON，而账本在残缺时价值最高。
- 渲染：默认只显示决策点，`--full` 才显示全量。一次 20 步的 run 全量打印没人读得下去。
- 回放：`ReplayLLM` + 真实工具，比较状态是否一致。
- 导出：映射到 OpenTelemetry 的 `gen_ai.*` 语义约定。

**回放的边界要讲清楚**：它保证「输入相同 → 决策相同」，不保证「结果相同」。
工具会真的再执行一次（文件可能被改过、时间变了）。所以回放的价值不是「拿到一样的答案」，
而是「把当时的推理链重新走一遍，看它从哪一步开始跑偏」。

### 5.7 评测（`eval/`）

- 每条任务一个**临时仓库**（复用目录会让残留导致假通过，这种假阳性最难发现）。
- 每条任务一份**独立账本**（失败时第一件事是看账本，不是加 print）。
- 检查项确定优先：文件内容、退出码、账本里有没有那条事件。
- 主观维度才上 LLM 判分，且必须钉住 judge 的模型与版本。

**mock 与 live 必须分开报**：mock 证明管道、策略、账本；live 证明模型能力。
混在一起宣称「100% 通过」是耍流氓，这条要写进 README。

### 5.8 MCP（`mcp/`）

stdio + JSON-RPC 2.0，一行一个消息。只用标准库：

- 一个读线程把 stdout 每行塞队列（Windows 没有 select，别指望非阻塞读）；
- stderr 单独线程排空，否则管道写满会让子进程卡死（真实踩过）；
- 超时按「等不到响应」算失败。

**MCP 工具一律标 `mutating=True`**：协议上无法知道对面会不会改状态，
「不知道」必须按「会改」处理。

## 6. 关键决策与代价

| 决定 | 为什么 | 代价 | 替代方案为什么没选 |
|---|---|---|---|
| 零运行时依赖 | 装到别人机器/CI 上，每多一个依赖就多一个劝退理由 | HTTP、SSE、JSON-RPC 全自己写 | httpx + pydantic 更快，但让 `pip install` 变重 |
| 文件当状态源 | 可 `ls`、可 `cat`、任何语言可读 | 没有事务、没有并发索引 | SQLite 更快，但账本要能被人直接打开 |
| JSONL 账本 | 追加写、坏行可跳过、可 `tail -f` | 没有索引，全量扫描 | SQLite/OTLP 后端更专业，但引入部署成本 |
| 压缩用确定性摘要 | 可复现、零成本、不漂移 | 信息量低，长任务丢细节 | LLM 摘要效果好，但让回放与成本都变复杂 |
| mock 优先的评测 | 无需 key、秒级、可进 CI | 不测模型能力 | 只做 live 评测，则 CI 无法运行 |
| 应用层策略 | 实现简单、可解释、跨平台 | 不防恶意逃逸 | 容器沙箱更硬，但 v0.1 的定位是本地工具 |
| 脚本化 demo | 现场演示可控、每次一样 | 不展示真实模型 | 真模型演示会超时、会失败、会尴尬 |
| 顺序执行工具 | 简单、日志线性可读 | 慢 | 并发调用更快，但账本的可读性会显著下降 |

## 7. 已知失败模式（还没解决的）

面试时这一段比「我的项目多牛」值钱：

1. **不是沙箱**：`shell` 能跑任意代码，恶意模型可绕开路径检查。
2. **没有流式**：长输出时用户干等，也没有「思考中」的反馈。
3. **单工作区、单进程**：一个工作区只应有一个执行者；多 agent 抢占要靠 keepwatch 那层。
4. **压缩会丢细节**：确定性摘要只保留「谁调了什么」，不保留「看到的内容」。
5. **token 是估算**：与真实计费可能差 10%，成本数字只能当量级看。
6. **平台差异**：demo 里的 `del /f` 是 Windows 命令；Unix 上会走到别的分支。
7. **回放不保证结果一致**：工具会真的再执行一次。
8. **没有跨 run 记忆**：每次运行都是白纸，长期项目的上下文复用没做。

## 8. 与同类的关系

| 对比对象 | 关系 |
|---|---|
| Claude Code / Codex CLI | 同类（都是 harness），但它们是产品；auditloop 的差异是**把账本与验证门禁当一等公民**，并且可离线演示 |
| OpenHands / SWE-agent | 它们是研究/工程平台，重沙箱与评测基准；auditloop 只有 9 个工具，刻意窄 |
| Temporal | 工业级工作流引擎，要服务端 + SDK。auditloop 是零依赖的缩小版，只保留「租约式」的收尾纪律 |
| LangGraph 等框架 | 它们是**建材**，你是用它搭；auditloop 是**车**，你是开它 |

一句话：**别人做「让 agent 更强」，我做「让 agent 的行为可被相信」。**

## 10. 面试讲法

### 30 秒

> 我做了个 coding agent 的运行时，解决的问题是「模型说它干完了，但没有任何证据」。
> 三个机制：策略层拦住危险操作；账本把每次模型调用和工具执行都记成 JSONL，能渲染能回放；
> 收尾必须跑一条验证命令，rc 不为 0 就记成「未验证」，不算完成。
> 零依赖，72 项测试，7 条评测里 3 条专门测失败路径。

### 3 分钟（按这个顺序）

1. **问题**：agent 的三类静默失效——乱来、假完成、不可查。报错不可怕，什么都没发生才可怕。
2. **机制**：一个循环 + 三道闸门（预算、策略、验证）+ 一本账。
3. **最难的地方**：不是写循环，是**定义「什么算完成」**。最后落到「账本里得有一条 rc=0」。
4. **踩过的坑**：压缩时从中间硬切会让 tool 消息失去 tool_call，上游直接 400；
   账本读到半行就崩，改成坏行跳过——账本在残缺时价值最高。
5. **边界**：它不是沙箱，防的是无意越界不是恶意逃逸；没有流式；回放不保证结果一致。

### 高频追问与答法

| 追问 | 答法 |
|---|---|
| 和 Claude Code 有什么区别 | 同类不同取舍：它服务交互体验，我服务事后审计。我的账本能回放、能进 CI 门禁。 |
| 为什么不直接用 LangGraph | 图编排解决的是「多分支编排」，我的问题用不到。引入框架会让「它到底做了什么」变得难查。 |
| 怎么证明它有用 | 三条失败路径的评测：被拒三次要停手、验证不过要记 unverified、步数到顶要收尾。跑 `auditloop eval run` 就能看到。 |
| 你这个是玩具吗 | 工具集窄、没有沙箱、没有流式——这些是**明知的边界**，写在 docs/design.md 第 7 节。窄是有意的：9 个工具足够改代码，多了就是攻击面。 |
| 如果给你三个人三个月 | 先补沙箱与流式，再做 eval 的 judge 与回归看板，最后做 HTTP 层与预算熔断。见 docs/roadmap.md。 |
