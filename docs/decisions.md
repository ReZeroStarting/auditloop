# 待定决策清单

> 用法：不用一次答完。每条都有**推荐项**和**代价**，你只需要说「这条按推荐」或者「我选另一个」。
> 编号是稳定的，以后可以直接说「D5 改成 B」。

---

## D1 · 第一版接哪个真实上游？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）DeepSeek** | OpenAI 兼容、便宜、国内直连、工具调用稳定 | 需要实名与充值 |
| B. OpenAI | 生态最全，函数调用最成熟 | 网络与费用 |
| C. 本地 Ollama | 零成本、可离线 | 小模型的工具调用经常格式错，会污染「是 harness 的问题还是模型的问题」的判断 |

**推荐理由**：先用便宜且兼容性好的上游，把「harness 有问题」和「模型不行」分开。

## D2 · 流式输出做到哪一层？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）只做渲染层** | `llm.chat(..., on_delta=...)`，决策层仍拿完整消息 | 需要改 OpenAI 兼容解析（SSE 逐块） |
| B. 决策层也流式 | 边收边判工具调用 | 工具调用参数是增量 JSON，解析复杂度陡增，容易出隐蔽 bug |
| C. 先不做 | 保持一次性返回 | 长任务时用户干等，演示观感差 |

**推荐理由**：流式是体验问题，不是正确性问题。让它待在渲染层，账本和回放都不受影响。

## D3 · 子 agent：实现还是删掉接口？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）实现** | `task` 工具起一个隔离上下文的子循环，只回传结论 | 递归、预算分摊、账本嵌套都要设计 |
| B. 删掉 | 骨架里现在会抛「P2 未实现」 | 少一个能讲的设计点；大范围探索时上下文会被噪音撑爆 |
| C. 保留接口不实现 | 现状 | 评审时容易被问「这个工具为什么存在」 |

**推荐理由**：「把噪音留在外面」是这个项目里少数真正属于 agent 工程的设计，值得做。

---

## D4 · 沙箱：上容器还是守住应用层？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）守住应用层，但把边界写清楚** | 现在这样，文档里明说「不防恶意逃逸」 | 不能跑不可信代码 |
| B. 可选 docker | `--sandbox docker` 时 shell 进容器，宿主只读挂载 | 用户要装 Docker；Windows 上路径映射麻烦 |
| C. 进程级限制 | Windows Job Object / Linux seccomp | 平台差异大，工作量远超收益 |

**推荐理由**：这个项目的定位是「本地可信环境下的可靠性」，不是「多租户沙箱平台」。承认边界比假装安全值钱。

---

## D5 · 压缩策略要不要升级？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）两级：先确定性，再 LLM** | 默认零成本摘要；仍超预算才调模型，账本记 `strategy` | 多一条代码路径，回放要区分来源 |
| B. 一直用确定性摘要 | 现状：可复现、零成本 | 长任务丢细节 |
| C. 一直用 LLM 摘要 | 效果好 | 压缩本身漂移、烧钱、回放不可复现 |

**推荐理由**：默认路径必须可复现。LLM 摘要只作为「兜底的兜底」。

---

## D6 · 评测要不要引入 LLM 判分？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）只给主观维度用，且钉版本** | 代码类任务继续用确定性检查；「回答质量」才上 judge | 需要两套报告格式 |
| B. 全面 LLM 判分 | 一条尺子量所有 | 尺子自己会漂，改动无法归因 |
| C. 不引入 | 全确定性 | 无法评「改得好不好」这类问题 |

**推荐理由**：能确定性判的，绝不用模型判。判分器一变，历史数据就失去可比性。

---

## D7 · MCP 只做客户端，还是也做服务端？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）先只做客户端** | 消费别人的工具 | 自己的工具不能被别的 agent 用 |
| B. 也做服务端 | 把 fs/grep/shell 暴露成 MCP 服务，别的 agent 可挂 | 权限模型要重新想一遍（远程调用没有本地路径监狱） |

**推荐理由**：客户端是当下的真需求；服务端意味着把「策略层」暴露到进程外，不是加个 handler 那么简单。

## D8 · 多上游路由要不要现在启用？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）先留着，不上主路径** | `FallbackLLM` 已实现，单上游跑稳再说 | 少一个卖点 |
| B. 立刻做主备 | primary → secondary 自动切换 | 两套 key、两套价格、账本要记「这次是谁答的」 |

**推荐理由**：降级链的正确性很难验证（你没法稳定复现 429）。先把单上游的边界摸清。

## D9 · 账本只留 JSONL，还是加可选后端？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）JSONL 为唯一真相，导出另算** | `trace otel` 导出给别人看 | 大规模检索不方便 |
| B. 可选 SQLite | 查询快、可索引 | 引入 schema 迁移，账本不再能 `cat` |
| C. 直接推 OTLP | 接现成可观测平台 | 需要 collector，本地开发体验变差 |

**推荐理由**：「能被人直接打开」是这个账本最重要的性质。

## D10 · 发布节奏？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）0.1.0 先发 PyPI，再用 0.2.0 发流式** | 名字已确认可用；早发布早暴露安装问题 | 0.1 不完美，会有人装到 |

**推荐理由**：安装问题只有发布才会暴露（keepwatch 的经验）。

## D11 · 演示要不要做成可录制的形式？

| 选项 | 说明 | 代价 |
|---|---|---|
| **A（推荐）终端录制 + 文档里的 GIF** | 60 秒，脚本化 demo，每次都一样 | 需要一个录制工具（asciinema / vhs / 录屏） |

## 实测结论（2026-10-31）

- **D1 上游**：已定。DeepSeek 实测可用（probe 1172ms，带 tools/usage/cache），live 评测 5/5。
  其余平台仍只有资料，没有证据。
- **D2 流式**：已定。只做渲染层（`stream=True` + `on_delta`），循环、账本、回放不受影响。
- **D6 评测**：有了新证据。三条断言「模型会犯错」的用例改为 `mock-only`——
  真实模型会拒绝删库、会真的修好测试。判分器必须说清它在测什么。
- **D10 发布**：打包与自包含验证已完成；PyPI 首发仍待账号侧登记。
- **D12 keepwatch 集成**：已定。只做最窄的一种（`keepwatch run -- auditloop ...`），
  不双向耦合，见 [integration-keepwatch.md](integration-keepwatch.md)。
