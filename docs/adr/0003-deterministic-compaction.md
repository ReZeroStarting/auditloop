# ADR 0003：上下文压缩用确定性摘要，不调模型

- **状态**：已采纳
- **日期**：2026-10-31

## 背景

长任务里上下文一定会满。三种常见做法：滑动窗口丢弃、调用模型做摘要、规则化摘要。

约束条件来自这个项目自己的承诺：**账本要能回放**。

## 决定

超水位时，把要丢弃的消息压成一段**规则生成的摘要**：

```
【上下文压缩摘要｜由 auditloop 生成，不是用户输入】
- 用户：修一下 divide 的除零行为
- 调用工具：fs_read, grep
- 观察：...（首行）
```

三个细节是刻意的：

1. 摘要头部写明「不是用户输入」——不写，模型会把摘要当成新指令，行为立刻跑偏；
2. 已有摘要会被**合并**而不是嵌套，避免出现「用户：用户：用户」；
3. 压缩点对齐到 assistant 边界，保证 `tool` 消息不失去它的 `tool_call`。

## 后果

**好处**

- 可复现：同样输入，压缩结果每次都一样，回放才有意义。
- 零成本：压缩不烧 token，预算全花在干活上。
- 不漂移：换模型不改变压缩行为。

**代价**

- 信息量低：只保留「谁调了什么」，不保留「看到的内容」。长任务后期，模型会忘记早期细节。
- 对中文/英文的长度控制粗糙，只能靠条数截断。

## 替代方案

| 方案 | 为什么没选 |
|---|---|
| 调模型摘要 | 效果好，但压缩本身漂移、烧钱，且回放不可复现——和「账本」这个卖点直接冲突 |
| 只做滑动窗口 | 最省事，但会丢掉任务目标，模型会原地打转 |
| 向量检索历史 | 需要 embedding 依赖，破坏零依赖；且检索结果顺序不确定，同样伤回放 |

## 什么时候应该重新考虑

当「确定性摘要」被证明是长任务失败的主因时（判据：live 评测里失败案例的账本显示模型在压缩后重复劳动）。
届时的做法应该是**两级**：默认确定性摘要，只有当摘要后仍超预算时才升级为模型摘要，
并在事件里记 `strategy: "deterministic" | "llm"`——让回放能分辨来源。
