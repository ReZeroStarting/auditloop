# ADR 0002：账本用逐行 JSON 文件，不用数据库

- **状态**：已采纳
- **日期**：2026-10-31

## 背景

需要记录一次运行里所有值得追问的瞬间：模型请求/响应、工具调用/结果、策略判定、上下文压缩、验证。
候选存储：JSONL 文件、SQLite、OTLP 推送、内存 + 导出。

这个账本有三种读者：**人**（`cat` / `tail -f`）、**命令行工具**（`trace show` / `replay`）、
**别的程序**（导出到可观测平台）。

## 决定

一个 run 一个 append-only JSONL 文件：`<state>/runs/<run_id>.jsonl`，一行一个事件，每条写完 flush。

事件形状固定为 `seq / ts / run_id / type / span / parent / payload`。

## 后果

**好处**

- 任何人 `cat` 就能读，不需要装任何东西；这一点在排障时价值最高。
- 追加写 + flush：进程被 kill 时，最后一条完整事件仍然是完整的。
- 坏行可以跳过（`read_events` 已实现）：账本在**残缺时**价值最高，不能因为半行就读不了。
- 备份、grep、上传、diff 都是现成的。

**代价**

- 没有索引，全量扫描；十万条事件的 run 会慢。
- 没有事务，并发写同一文件会交错（当前设计是「一个 run 一个文件、单写者」）。
- 跨 run 的聚合查询要自己遍历文件。

## 替代方案

| 方案 | 为什么没选 |
|---|---|
| SQLite | 查询快，但账本不再是「能直接打开的文件」，且引入 schema 迁移 |
| 直接推 OTLP | 需要 collector，本地开发与离线演示全部失效 |
| 内存 + 结束时写盘 | 进程一死全丢——恰好丢掉最想知道的那段 |

## 什么时候应该重新考虑

1. 单 run 事件数稳定超过 10 万（当前的压缩与渲染都会先卡住）；
2. 需要跨 run 的实时聚合（比如「这个模型最近一周的失败率」）——那时应该加**可选**的 SQLite/OTLP 旁路，
   而不是替换 JSONL：把 JSONL 留作唯一真相，旁路只做索引。
