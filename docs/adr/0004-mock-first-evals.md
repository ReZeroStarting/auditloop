# ADR 0004：评测以 mock 为主，live 单独列

- **状态**：已采纳
- **日期**：2026-10-31

## 背景

评测有两种跑法：

- **mock**：用脚本化的假模型，确定性、秒级、不要 key；
- **live**：接真实模型，慢、要钱、结果不稳定。

常见做法是把两者合成一个「通过率」，看起来更漂亮。

## 决定

两者**分开跑、分开报**，永不合并成一个数字。README 里只放两行：

- `mock`：证明管道、策略、账本（当前 7/7）；
- `live`：证明模型能力（当前**无**，P3 之后才有，且数字必须写实）。

## 后果

**好处**

- mock 能进 CI：每次提交都跑，回归立刻可见。
- 失败可归因：mock 挂了是代码问题；live 挂了可能是模型问题。合成一个数字，就永远分不清。
- 不撒谎：README 里没有「通过率 100%」这种把管道测试当成模型能力的表述。

**代价**

- 需要维护两套运行路径（`run_tasks(mode=...)`）。
- mock 的脚本要跟着工具集演进，否则会变成「测试了不存在的调用」。

## 替代方案

| 方案 | 为什么没选 |
|---|---|
| 只做 live | CI 里跑不了（要 key、要钱、可能被限流），回归形同虚设 |
| 只做 mock | 无法回答「换个模型还行不行」 |
| 合并报告 | 数字好看，但失去全部诊断价值 |

## 什么时候应该重新考虑

当 live 评测能够稳定复现（同一模型、同一温度、通过率波动 < 5%）时，
可以把 live 也放进 CI（每周一次），但**报告仍然分开**。
