# ADR 0005：策略在应用层，不做沙箱

- **状态**：已采纳（有明确边界）
- **日期**：2026-10-31

## 背景

一个能执行 `shell` 的 agent，本质上是「把命令执行权交给模型」。三种防护：

1. **应用层策略**：解析命令、路径检查、白/黑名单；
2. **操作系统级隔离**：容器、namespace、seccomp、Job Object；
3. **权限最小化**：只跑在只读挂载、无网络的沙箱里。

## 决定

v0.1 只做第 1 种：

- 破坏性命令**硬拒绝**（不需要问人，直接不执行）；
- 只读命令在所有模式下放行；
- 会改状态的命令按 `ask` / `never` / `auto` 处理；
- 文件路径必须在工作区内（`ToolContext.resolve` 强制）。

## 后果

**好处**

- 零依赖、跨平台、可解释：用户能看懂为什么被拒（拒绝原因会写进账本）。
- 对「模型无意越界」有效：这是绝大多数真实事故的形态（模型想图省事删个文件）。
- 不需要用户装 Docker。

**代价**

- **不防恶意**。`shell` 能执行任意命令，一个有恶意的模型可以绕开路径检查
  （例如 `python -c "open('/etc/passwd')"`）。这一点必须写在 README 和 SECURITY 里，
  而不是靠用户自己发现。
- 命令分类靠启发式（首 token + 子命令），`bash -c "..."` 这类包装能骗过它。

## 替代方案

| 方案 | 为什么没选 |
|---|---|
| Docker 沙箱 | Windows 路径映射与用户体验成本高；v0.1 的定位是本地可信环境 |
| seccomp / Job Object | 平台差异巨大，工作量远超收益 |
| 干脆不给 shell 工具 | 那它就不是 coding agent 了 |

## 什么时候应该重新考虑

当出现下面任一场景：

1. 要跑在不可信仓库上（比如「让用户提交一个仓库，agent 去修」）；
2. 要做成服务（多租户，模型可能被注入攻击）；
3. 出现第一起「模型主动绕开策略」的真实案例。

届时做法是**加**一层容器执行（`--sandbox docker`），而不是把应用层策略删掉：
两层解决的是不同问题——应用层解释「为什么不行」，容器层保证「不行也做不到」。
