## 0. 什么算「做完」

v1.0 的判据（五条全满足才算）：

1. `pip install auditloop` 之后，**没有 API key** 也能跑 `auditloop demo` 并看到完整账本。
2. 配好 key 之后，能在**真实仓库**上跑一次任务，`--verify` 通过，退出码 0。
3. `auditloop eval run --mode live` 有**真实的通过率数字**写进 README（不美化、不挑模型）。
4. 一次运行能 `trace replay` 复现，状态一致；`trace verify` 能报出账本自洽性。
5. 文档里没有一句「将来会有」当成「已经有」；每个数字都能用一条命令复现。

不追求的：多租户、Web 产品、容器沙箱、比 Claude Code 强。这些写进 `docs/decisions.md` 的「不做」。

## 2. P1 文档：写什么、为什么

现在只有 3 份文档（372 行），对「能看懂」够，对「开源项目该有的样子」不够。

| 文件 | 解决谁的疑问 | 关键内容 |
|---|---|---|
| `README.md`（改英文，中文拆到 `README.zh-CN.md`） | 国际受众、HR | 一句话定位、30 秒 demo、架构图、退出码表 |
| `docs/providers.md` | 「能接我的模型吗」 | 12 家 base_url + 参数差异 + 已知坑；OpenAI 兼容 vs 原生协议的边界 |
| `docs/api.md` | 「我要二次开发」 | `run_loop` / `Registry` / `Policy` / `TraceWriter` 的签名与最小示例 |
| `docs/architecture.md` | 「它怎么转」 | 分层图 + 一次 run 的时序（比 design.md 更偏结构） |
| `docs/adr/0001-*.md` … `0005` | 「为什么不用 X」 | 零依赖 / 文件当状态源 / 确定性压缩 / mock 评测 / 应用层策略 |
| `SECURITY.md` | 「能跑 shell 的东西安全吗」 | 威胁模型：防无意不防恶意；报告方式；不要在不可信仓库直接跑 |
| `CONTRIBUTING.md` | 「我能帮什么」 | 跑测试、加工具、加评测任务的步骤 |
| `docs/faq.md` | 排错 | 「一直说参数错」「模型不调工具」「账本半行」等 |

**数字一致性**：现在文档里写死「105 项测试」。P1 加一个 `tools/docs_check.py`，
从 `pytest --collect-only` 和 `tasks/eval.jsonl` 里读出真实数字，和文档里的数字比对，不一致就退出 1。
这件事本身就是个好细节：**文档里的数字应当是检查出来的，不是承诺出来的。**

## 3. P2 原型：为什么是 HTML，而不是 Figma

| 做法 | 优点 | 为什么不用 |
|---|---|---|
| Figma / 画图 | 好看得快 | 交付物是图片，不能点；改一次要重画 |
| React + Vite | 工程正确 | 为了看一个界面引入构建链，面试时不好现场开 |
| **单文件 HTML（选它）** | 双击就开、可发链接、可嵌 GitHub Pages、能喂真数据 | 需要自己写点 CSS/JS |

### 原型的三块界面

1. **运行时间线**：左边事件流（模型调用 / 工具 / 拒绝 / 压缩 / 验证），右边当前上下文水位条。
2. **账本详情**：点任意事件展开完整 payload；顶部显示 `seq` 连续性（断号会标红）。
3. **失败态**：单独两个状态页 —— `unverified`（验证失败）和 `policy_blocked`（连撞三次）。这两个是项目的卖点，必须在原型里能看见。

### 数据从哪来

**不手画数据。** 先加一条命令（约 30 行）：

```bash
auditloop trace export demo --format html-data > prototype/data/demo.json
```

原型读这个 JSON。这样原型和产品永远同源，也顺带成为 `trace` 子命令的第一个真实消费者。

## 4. P3/P4 开发：按「能答上追问」排序，不按功能多少

| 顺序 | 做什么 | 面试官会问的问题 | 没做会怎样 |
|---|---|---|---|
| 1 | 多上游 + 能力探测 | 「接我的模型行吗」 | 只能演示 DeepSeek 一家 |
| 2 | 流式 | 「为什么它半天没反应」 | 观感差，且无法展示 token 级延迟 |
| 3 | live 评测矩阵 | 「你怎么知道换个模型还work」 | 只有 mock 数字，不可信 |
| 4 | `trace verify` | 「账本自己坏了怎么办」 | 可观测性的地基不牢 |
| 5 | 会话续跑 | 「跑一半断了怎么办」 | 只能整段重跑，烧钱 |
| 6 | 子 agent | 「大范围搜索怎么控上下文」 | 上下文会被噪音撑爆 |

**刻意排后面的**：容器沙箱（Windows 路径映射容易吃三天）、HTTP 层、评测看板。

## 5. 风险与回退

| 风险 | 概率 | 影响 | 回退方案 |
|---|---|---|---|
| 真模型的 tool_calls 格式不兼容 | 高 | live 评测跑不起来 | 加「宽松解析 + 明确报错」，并在 providers.md 记下每家实测 |
| 流式解析踩 SSE 分帧坑 | 中 | 卡 1 天 | 先做「伪流式」（拿到完整响应后按字回放），接口不变 |
| 文档数字随代码漂移 | 高 | 可信度受损 | `docs_check.py` 进 CI |
| 原型做完没人看 | 中 | 白花一天 | 先发 GIF 到 README，再补原型 |
| 你的方向变（不投 AI 岗了） | 低 | 全盘 | P3 之前都能停在「可发布」 |

## 6. keepwatch 在其中的角色

D12 决定「要不要真集成」。实测之后（2026-10-31，见对话记录）结论是：**可以用，但只用在长跑场景**。

- 用它管 P3/P4 的开发任务是可以的：`send` → `run` → 账本留痕，`checkpoint` 写交接说明，`doctor` 做自检。
- 但它的 `--json` 没有文档化 schema，作为「给 agent 消费的接口」还差一层；
- 认领未初始化的 agent 会抛裸 traceback（应该是一个明确的「未知 agent」错误 + 非零退出码）；
- `check` 的排序（新→旧）和 `run` 的取用顺序（旧→新）相反，人读列表会预测错下一条。

所以集成只在 **P5** 做最窄的一种：auditloop 作为 keepwatch 的 worker（`keepwatch run --who auditloop -- auditloop run ...`），
**不做双向耦合**，两边账本各自独立。理由：两个工具都还在演进，强耦合会互相拖死。
